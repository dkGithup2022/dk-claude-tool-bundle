# tool-assess-port

## 0. 배경

Claude Code 에서 쓸 수 있는 로컬 도구(Python CLI + Claude 플러그인)를 만드는 스킬 모음(dk-claude-tool-bundle) 중 port 층을 평가하는 스킬이다.
port 는 바깥 데이터(바깥 API, 로컬 파일)를 다루는 패키지다. 워크플로와 다른 코드는 바깥 데이터를 port 를 거쳐서만 읽고 쓴다.
`tool-planner` 가 기능 요청을 받으면 먼저 이 스킬로 "필요한 바깥 데이터 접근이 이미 있는 포트로 되는가"를 판정한다. 이미 있는 것을 다시 만들지 않고, 바꿀 때는 최소로 바꾸기 위해서다.
판정 결과와 포트 계획을 계획서에 적고, 필요한 도메인 데이터는 `tool-assess-model` 에 넘긴다. 코드는 쓰지 않는다.

더 읽을 곳: `${CLAUDE_PLUGIN_ROOT}/README.md` (프로젝트 구조와 패키지 규칙), `${CLAUDE_PLUGIN_ROOT}/skills/tool-add-port/SKILL.md` (포트의 모양과 규칙).

## 1. 이 스킬의 목적

요청을 처리하는 데 필요한 바깥 데이터 접근을 기존 포트로 할 수 있는지 판정하고, 계획을 계획서에 적는다. 코드는 쓰지 않는다.

- **입력**: 계획서(`specs/plans/{요청 이름}.md`)의 `요청` 절, 그리고 `specs/ports.md`, `specs/models.md`
  (`specs` 문서가 없으면 `src/{pkg}/port/`, `src/{pkg}/model/` 소스를 읽어 판단한다)
- **산출물**: 계획서의 `### tool-assess-port` 절

## 2. 평가 절차

### 2.1 필요한 접근을 나눈다

요청에서 바깥 데이터 접근을 하나씩 뽑는다. 하나는 "무엇을, 어디서, 읽는지 / 쓰는지"다.

예: "GitHub 이슈 목록을 읽어 일정으로 저장한다" →
- GitHub 이슈 목록 읽기 (바깥 API)
- 일정 저장 (로컬 파일)

### 2.2 접근마다 기존 포트를 확인한다

| 판정 | 기준 | 이어서 할 일 |
|---|---|---|
| 충족 | 같은 대상의 포트가 있고, 필요한 메서드도 있음 | 없음. 있는 메서드를 적는다 |
| 부분 충족 | 같은 대상의 포트는 있지만 메서드가 없음 | 기존 인터페이스에 메서드 추가 계획 |
| 미충족 | 같은 대상의 포트가 없음 | 새 포트 계획 |

같은 대상인지는 저장 위치(파일) 또는 서비스(API)가 같은지로 본다. 비슷한 메서드가 이미 있으면 새로 만들지 말고 그것을 쓸 수 있는지 먼저 적는다.

### 2.3 model 층에 필요한 것을 판단한다

메서드가 주고받는 데이터마다 정한다.

| 데이터 | 둘 곳 | model 층 요청 |
|---|---|---|
| 우리가 주로 다루는 데이터 (도메인 데이터) | `model/` | 있으면 그대로, 없거나 필드가 모자라면 요청 |
| 응답 모양, 조인 결과처럼 주체는 아니지만 스펙으로 가지고 있어야 하는 것 | 그 포트의 `dto/` | 없음 (포트 안에서 만듦) |

### 2.4 포트 계획을 세운다

새로 만들거나 바꾸는 포트마다 정한다.

- 폴더: 로컬 파일은 `port/local/{대상}/`, 바깥 API 는 `port/{서비스}/`
- 인터페이스: Reader 만인지, Writer 도 있는지. 메서드마다 이름, 인자, 돌려주는 값, 없을 때·실패할 때
- 변환기: 파일이면 `to_file` / `to_data`, API 면 `to_{dto 이름}` / `to_{요청 이름}_body`
- 파일 포트: 저장 위치(데이터 폴더 아래 경로)
- API 포트: 호출 방법(CLI 또는 HTTP), 인증, 환경 변수(`{PKG}_{서비스}_BIN` / `_URL` / `_TOKEN`), 새 의존성 필요 여부
- dto 목록과 필드
- 기존 인터페이스를 바꾸는 경우: 바뀌는 구현과 쓰는 곳 (`grep` 으로 찾음)

## 3. 규칙

- 코드를 쓰지 않는다. 계획만 적는다.
- 포트는 `model` 과 `common` 만 쓴다. 계획에 engine·workflow·claude_utils 의존을 넣지 않는다.
- 메서드는 model 이나 dto 를 돌려준다. `dict` 를 돌려주는 계획을 세우지 않는다.
- 새 라이브러리가 필요한 계획이면 계획서에 "사용자 확인 필요"로 적는다.
- 기존 메서드의 이름·인자·돌려주는 값이나 파일 저장 모양을 바꾸는 계획이면, 바꾸기 전과 후를 적고 "사용자 확인 필요"로 표시한다.
- 요청이 "순서대로 여러 단계를 실행"하는 일(묻고, 프롬프트를 부르고, 반복하는)이면 포트가 아니라 워크플로다. 계획서에 "워크플로 제작 스킬로 넘김"이라고 적고 그 부분은 평가하지 않는다.

## 4. model 층에 요청할 때의 형식

`tool-assess-model` 이 그대로 받을 수 있게 아래 형식으로 적는다.

```
- 대상: {도메인} (신규 / 기존 확장)
- 클래스: {클래스 이름} ({도메인}/{파일 이름}.py)
- 필드: {이름}: {타입}, ... (기존 확장이면 더할 필드만)
- 동작: {메서드 이름}(...) -> {클래스} (있으면)
- 쓰는 곳: {포트 이름}.{메서드 이름}
- 이유: {왜 필요한지 한 줄}
```

## 5. 산출물

계획서의 `### tool-assess-port` 절에 아래를 적는다.

```markdown
### tool-assess-port

**판정**: 충족 / 부분 충족 / 미충족

**접근별 판정**

| 접근 | 판정 | 포트 | 메서드 |
|---|---|---|---|
| GitHub 이슈 목록 읽기 | 미충족 | gh (신규) | GhReader.list_issues(owner, name) -> tuple[GhIssue, ...] |
| 일정 저장 | 충족 | local/todo | TodoWriter.save_all(todos) |

**포트 계획**

- [신규] port/gh/
  - GhReader.list_issues(owner: str, name: str) -> tuple[GhIssue, ...]  — 없으면 빈 튜플, 실패하면 GhApiError
  - 호출: gh CLI (`gh api repos/{owner}/{name}/issues`), 환경 변수 {PKG}_GH_BIN, 새 의존성 없음
  - 변환기: GhApiConverter.to_issue(body) -> GhIssue
  - dto: GhIssue(number: int, title: str, created_at: str)

**model 층 요청**

- 없음 / (4 절 형식으로)

**사용자 확인 필요**

- 없음 / (항목)
```
